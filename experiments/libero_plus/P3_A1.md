# P3-A1: paired Scale-only / RIPT actions

## Scope and audit

This is a two-case Camera Viewpoints smoke, not the 18-case experiment. One source
policy generates both trajectories. Replay evaluates both policies on precisely
the same saved inputs. No representation learning or P3-B is implemented.

Audited existing paths (unchanged):

- `evaluate.py`: Plus revision `4976dc30028e805ff8094b55501d532c48fec182`, exact
  2,591-entry mapping, task order zero, seed before each task, environment seed
  zero, initial state index zero, ten dummy steps, 300 policy steps, and an
  eight-action queue. The new loop consumes each eight-action chunk in order,
  stopping on success or horizon, which is equivalent to that queue.
- Both Scale and RIPT use `OpenVLA_OFT_Policy` and
  `get_vla_action_batch(..., use_laplace_sampling=False, scale_factor=1.0)`.
  Scale loads the same OFT base, base action head and proprio projector; RIPT
  additionally loads the released LoRA adapter and `openvla_headers.pt` action
  and scale heads. Both load `dataset_statistics.json`. Model sync writes are
  disabled exactly as in the evaluator.
- Both use RIPT's prompt-prefix KV cache followed by the action-token pass and
  its module-level SDPA patch. **No full-sequence OFT control is used here.**
  Capture, Scale replay, and RIPT replay use separate processes.
- `prepare_observation` rotates both camera images, resizes from 256 to 224, and
  assembles eight proprio values. The RIPT helper subsequently center-crops the
  prepared images and normalizes proprio. Saving before that helper avoids
  double cropping or normalization. The lowercase instruction prompt and both
  image paths are unchanged. No custom camera perturbation is synthesized: the
  selected official Plus task/environment supplies it.
- `compare_actions.py` only captures initial observations and compares SFT
  against Scale with extra full-sequence controls. Its serialization is useful
  context but its execution path is inappropriate for this experiment; it is
  neither modified nor invoked.

Action order was traced through the action head's `(batch, chunk, 7)` reshape,
the LIBERO RLDS transform preserving the first six components, and evaluator
postprocessing of the last component. Translation occupies indices 0–2, rotation
commands 3–5, and gripper 6. The repository pins robosuite 1.4.1; its
[OSC controller](https://github.com/ARISE-Initiative/robosuite/blob/v1.4.1/robosuite/controllers/osc.py)
and [single-arm controller dispatch](https://github.com/ARISE-Initiative/robosuite/blob/v1.4.1/robosuite/robots/single_arm.py)
confirm this split. Preflight verifies the **installed source**, and capture
asserts fixed six-dimensional delta OSC plus one gripper. A different controller
implementation fails explicitly instead of assuming its ordering. These rotation
metrics are command-space Euclidean differences, not geodesic orientation errors
or measured robot motion.

Use the existing environment; no package installation or checkpoint download is
performed by this module. Run from `/nfs4/jhkim/repos/vla-rlvr` after placing the

```bash

  python experiments/libero_plus/p3_action_analysis.py validate \
  --run-id p3-a1-camera-scale-smoke
```

To use RIPT as the source, replace `--source scale` with `--source ript` in dry-run
and capture and use a different run ID throughout. That is a separate optional
smoke, **not automatically scheduled**. One run contains one source, with metrics
explicitly grouped by source, shift and reproduced case class.

The default candidate path is `outputs/rlvr_analysis/p3/p3_case_candidates.csv`.
Auto-detection accepts a single `task_id` or `id` column containing **one-based**
Plus IDs. For any other schema, use `--id-column EXACT_COLUMN_NAME` on dry-run and
capture. There is no index-base guessing. Selection takes the first candidate in
CSV order for each Camera lost/gained transition, deriving that transition from
Scale and RIPT evaluation JSONs. Duplicate IDs, unknown IDs, conflicting recognized
CSV labels, mismatched task names/shifts or missing outcomes fail. The original
manifests must match the checked-in evaluator, checkpoint paths and protocol.

The 300-step bound is needed to reproduce a failed episode. `--horizon 16` is
available for an even smaller engineering check, but an unsuccessful truncated
trajectory is **not_verified_truncated**, even if the historical outcome was
failure. It never establishes a reproduced lost/gained case. At horizon 300,
two cases need at most 76 capture forwards, 152 replay forwards, and 600 policy
environment steps plus 20 dummy steps. Successful episodes stop earlier.
CPU provenance hashing reads the checkpoint files but never loads GPU weights.

Exit codes: 0 = valid and reproduced; 2 = invalid inputs/artifacts or unavailable
preflight prerequisites; 3 = completed capture/comparison with a reproduction
mismatch or unverified truncation. CUDA/runtime failures also exit nonzero.
A mismatch preserves its artifacts and may still be compared intentionally;
it is grouped under `reproduction_mismatch`, not `lost` or `gained`.
A failed partial run is not resumed or overwritten; use a fresh run ID.

## Artifacts and validation

- `metadata.json`: immutable protocol, seed, source, complete task mapping,
  candidate rows, historical result records and hashes, component/checkpoint
  paths and SHA256s, normalization statistics/key, implementation hashes and
  action-order evidence. Stored before GPU loading.
- `observations.npz`: one row per **policy query**, not every environment step:
  prepared full/wrist images, raw proprio, language, task ID, zero-based policy
  step, input SHA256, captured normalized mean, unnormalized action chunk,
  processed action chunk, and number of actions actually executed from it.
- `capture.json`: episode success/steps, comparison to historical source-policy
  outcome, explicit reproduction and analysis labels, initial-state digest,
  BDDL/init-file hashes, archive hash, input/output dtypes and runtime provenance.
- `scale_actions.npz`, `ript_actions.npz`: normalized means (BF16 results stored
  losslessly as float32), unnormalized and processed actions, input SHA256s,
  task IDs and query steps. Each action array is `N × 8 × 7`.
- `scale_worker.json`, `ript_worker.json`: model identity, loaded normalization
  key, dtype, versions, cached inference flag, implementation paths, worker PID
  and action archive digest.
- `summary.json`, `actions.csv`: paired metrics and reproduction labels. CSV has
  one row per predicted action slot, linked to its observation/query step; chunk
  L2 is repeated on its eight rows for convenience, not eight independent chunks.

Input hashes cover image/proprio names, dtypes, shapes, contiguous bytes, and
exact language before policy preprocessing. Replay verifies archive and per-input
hashes and uses fresh copies. Norm checks validate finite bounds and masks,
loaded statistics/key, the deterministic mean branch, quantile unnormalization,
and gripper postprocessing against returned actions. Action arrays must be finite
with exact shapes. Gripper postprocessing preserves the existing `-sign(2*g-1)`,
including the zero at `g == 0.5`.

Validation rechecks source/checkpoint provenance, task mapping, archive checksums,
input alignment, step accounting, reproduction labels, normalization, metrics and
CSV checksum without GPU work. Missing or changed prerequisites fail; arrays are
loaded with `allow_pickle=False`. Replay differences from the source capture are
reported separately in all three action spaces instead of hidden.

## Metric definitions and interpretation

For paired chunks A and B, action slot j uses `||A[j] - B[j]||₂`; chunk distance
is the Frobenius norm over all 56 values. Translation and rotation use indices
0:3 and 3:6, respectively. Results are computed separately in normalized,
unnormalized, and processed/executed command spaces. Gripper disagreement compares
the final processed gripper commands. Statistics include mean, median, p95, max,
and counts for slots, chunks, and per-observation means. Gripper includes its
overall disagreement rate and the distribution of per-observation rates.

Default aggregates include all eight predicted slots, including unused slots of
a final chunk. The `source_executed_steps` subset excludes those slots and marks
which actions were actually applied during capture. RIPT's replay actions are
counterfactual on Scale-source observations (and vice versa), not new rollouts.
The `analysis_case` grouping distinguishes reproduced lost/gained from mismatches
and truncations; `historical_case` remains available as historical provenance.

Action differences alone do not establish representation information loss or a
causal explanation for OOD failures. This smoke is a descriptive paired-input
check. It does not reproduce the other policy's trajectory, estimate significance,
or generalize from two cases to all 2,591 conditions.

## Diagnosing an incomplete capture

A run containing only `metadata.json` and `config-capture/config.yaml` has entered
worker setup but has no completed observation archive. It may still be running,
or it may have failed/interrupted; those two files alone do not distinguish them.
`dry-run.ready` reports CPU prerequisites only. `capture_can_start` also checks
whether the requested run directory already exists. Neither confirms GPU readiness.

```bash
python experiments/libero_plus/p3_action_analysis.py status --run-id p3-a1-camera-scale-smoke
pgrep -af '[p]3_action_analysis.py'
```

Do not start another capture while the old worker is still running. Once it has
failed/stopped, preserve its directory and use a fresh run ID. Compare requires
both `observations.npz` and `capture.json`. Repeating dry-run or compare cannot
create them. The initial failure cannot be diagnosed from a missing `capture.json`
message; inspect the original capture traceback.

New launches automatically stream and save combined stdout/stderr in `capture.log`
and `replay-{model}.log`, with return codes in matching `*-exit.json` files.
Older runs have no automatic log; the patch cannot recover their lost stderr.
Use the updated script for a fresh capture, then inspect `capture.log` if it fails.
Do not bypass provenance validation or replace metadata in the old run after
updating the script. Three CPU regression tests cover incomplete-run reporting,
failed-worker stderr/exit preservation, and successful worker logging.

### Camera virtual task filenames

Camera identifiers such as `open_the_middle_drawer_of_the_cabinet_view_1_15_100_0_0_initstate_0`
are virtual task names. The pinned Plus wrapper reads the viewpoint parameters
from the suffix and opens the base `open_the_middle_drawer_of_the_cabinet.bddl`.
The benchmark similarly loads `open_the_middle_drawer_of_the_cabinet.pruned_init`.
The earlier P3 validation incorrectly required the virtual filenames on disk.

The corrected validation resolves these physical files in CPU preflight and
capture provenance. It continues passing the original, unmodified Task to the
existing environment constructor and `suite.get_task_init_states`. No BDDL copies,
symlinks, checkpoint changes or perturbation changes are needed. The physical
paths/hashes are included in metadata. Tests cover both reported Camera names,
missing physical inputs, and preservation of the virtual Task in the capture loop.

Resolution is based on the pinned upstream
[environment wrapper](https://github.com/sylvestf/LIBERO-plus/blob/4976dc30028e805ff8094b55501d532c48fec182/libero/libero/envs/env_wrapper.py)
and [benchmark loader](https://github.com/sylvestf/LIBERO-plus/blob/4976dc30028e805ff8094b55501d532c48fec182/libero/libero/benchmark/__init__.py).
